Paper Link: http://arxiv.org/abs/2401.09670

The first paper that introduces PD disaggregation. Which separates inference of transformer models into Prefill and Decode.

# First Pass

## Why and What

In LLM applications there are usually two metrics called _time to first token_ (TTFT) and _time per output token_ (TPOT), and they are corresponding to different phase of LLM inference, _prefill and decoding_. Prefill is the phase that LLM generates the first token, and decoding is the following multi-step token generation. Prefill needs to be fast, making the application more interactive. Decoding also needs to be fast, at least faster than human reading speed.

Before this paper, prefill and decode tasks are put on the same GPU machine which is hard to optimize because their resource allocation are coupled together, so the LLM providers must over provide resource, which leads to low efficiency. In their experiments, both prefill and decode latency reduced a lot when served sololy.

What DistServe do is that they disaggregated prefill and decoding phase, which enables to serve up to 7.4 times more requests or 12.6 times tighter SLO (Service Level Objectives) under various latency constraints.

# Second Pass

## Background and Motivation

In the paper, they defined a target to optimize, which is called _per-GPU goodput_, defined as the maximum request rate that can be served adhering to the SLO attainment goal (say, 90%) for each GPU. provisioned.

### LLM Inference

Modern LLMs predict the next token given an input sequence. And _prefill_ step deals with a new sequence, process all tokens concurrently, which usually leads to computation-bound. While _decoding_ step is very different, each decoding step only processes the new token generated by previous step and keeps on generating the next one token, which leads to memory-bound.

Note that though in prefill step we may have KV-cache hit and can just load KV from cache but not compute them again, but that is in the scenario of modern agent (2026), however in this paper (2024), the mainstream is still about chatbot, or code completion, which might not have that much cache hit rate (or such KV-cache technique is not mature? TODO), so prefill stage is still compute-bound.

### LLM Serving Optimization

Before PD disaggregation, there are already methods to improve online serving. Like batching and model parallelism. But in previous scenario, we put prefill and decoding together, so any technique applied will be applied to the mixture of execution, which can be hard to balance. Also the batching and parallel strategies are various and complex, it can be hard to make progress.

For example, in model parallel, we have _tensor parallel and pipeline parallel_ ([[Distributed Training - TinyML]]), tensor parallel is called _intra-op_ and pipeline parallel is called _inter-op_ parallel in this paper. Intra-op parallelism split model weights of one layer (kind of like horizontal split) into different machines, and communicate the compute results, which speeds up execution, while inter-op parallelism split layers (vertically cut the model), mainly increases throughput.

So for prefill, which focuses on TTFT also is compute-bound, needs to reduce execution time to meet the tight SLO, in this case, intra-op parallelism is preferred. By contrast, the optimal parallelism configuration of the decoding phase depends on the running batch size. More details are in the following chapter.

## Tradeoff Analysis

In this section we are going to analyze the computational pattern of prefill and decoding instances _post disaggregation_.

### Analysis of Prefill Instance

**Batching strategy.** Prefill is typically compute-intensive. So when it reaches compute bound, batching would not work any more, and the workload depends on the input sequence length. In order to make sure batched workload does not exceeds compute bound, they have a dynamic batch strategy, first identify a threshold of sequence length $L_{m}$, batch more when under it.

**Parallelism plan.** This part involves detail assumptions and formula, recommend to go to original paper. The result is, when at lower rates, the execution time mainly contributes to latency, intra-op parallelism's reduction in execution time makes it more efficient. As the request rate increases and the queuing delay becomes more significant, inter-op parallelism becomes advantageous.

### Analysis for Decoding Instance

A decoding instance receives the KV caches and the first output token from the prefill instance and generates subsequent tokens one at a time. And our optimization goal is to satisfy the TPOT requirement using minimal compute resource.

**Batching strategy.** Since decoding is memory bound, we can batch more jobs together to increase GPU utilization. In the past, this is hard to realize, because it is coupled with prefill and prefill cannot be batched too much.

**Parallelism plan.** As the decoding batch size continue to increase to approach the compute-bound, the decoding computation resembles the prefill phase. Intra-op parallelism reduce latency and inter-op parallelism scale the throughput. When the TPOT SLO is stringent, intra-op parallelism is key to reduce TPOT to meet the latency goal. When it is loose, we are free to use some inter-op parallelism to enhance throughput.

### Practical Problems

**Variable prefill length.** In previous assumptions, the input sequence are of uniform length, which is impossible and different length will cause bubbles (idle), so in next section they designed algorithm that finds best parallelism based on workloads and resort to scheduling to minimize the bubble.

**Communication overhead.** Can be neglected in most case with intra-node NVLink, but for some case we don't have such high bandwidth, the author designs an alternative.

# Third Pass

## Method

### Algorithm

They call the result config with a fancy word "placement". And the method to find best placement is actually **enumeration**. They iterate over the number of GPUs in one intra-op parallelism node, then iterate over the inter-op parallelism count to find the highest average goodput based on their simulator's result. So intra-op parallelism required high speed bandwidth, so it happened inside one node, the iteration range will be from 1 to $M$, the number of GPUs in one node. And since then, the inter-op parallelism range will be from 1 to $\frac{M\times N}{\text{intra-op\_count}}$, how many intra-op group we have, we can split the model pipeline into that much stages.
